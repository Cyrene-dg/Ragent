# 原神 v7 元数据检索 A/B 测试报告（首轮）

## 结论

在相同 v7 语料、相同意图识别结果、相同 ES / Milvus / Rerank 链路下，只开启
`element` 元数据条件后：

| 指标 | Baseline：关闭 `element` | Candidate：开启 `element` | 变化 |
| --- | ---: | ---: | ---: |
| 单实体 / 别名题 Hit@5 | 100.00% | 100.00% | 0 |
| 单实体 / 别名题 MRR@10 | 1.0000 | 1.0000 | 0 |
| 单实体 / 别名题 Recall@20 | 100.00% | 100.00% | 0 |
| 三道元素集合题的实体覆盖率@20 | 28.10% | 100.00% | +71.90 个百分点 |
| 所有计分题 Top5 错误召回率 | 55.56% | 14.81% | -40.74 个百分点 |
| 检索延迟 P50 | 469ms | 225ms | -244ms |
| 检索延迟 P95 | 553ms | 552ms | 基本持平 |

本轮支持的结论是：`element` 过滤在“冰 / 火 / 风系角色有哪些”这类集合问题上明显减少跨元素资料，并没有让本轮单实体题漏召回。它没有让原本已经排在第一名的单实体资料进一步变好，因此不能把 Hit@5 的持平包装成“单实体检索提升”。

## 测试设计

- 时间：2026-07-26；运行标识：`pilot-20260726-final-150508`。
- 测试集：10 题。其中 5 道单实体或别名题、3 道元素集合题计入指标；1 道无实体泛问和 1 道领域外问题仅作诊断，不计入分数。
- 标注：单实体题以 `logical_chunk_key` 作为 Gold；集合题以预期 `entity_id` 集合计算覆盖率。试用角色副本仅在明确标有“试用”时归并到正式角色，不会把同名但不同实体强行合并。
- 执行：预热 3 次；每题运行 5 次。每条策略各有 40 个计分样本（5 道 Chunk 题 × 5 + 3 道集合题 × 5），两条策略合计 80 个检索分支样本。
- 对照：同一次请求先完成一次意图识别与实体解析；Baseline 和 Candidate 复用该结果，只在构建检索计划时分别关闭 / 打开 `element` facet。因此差异可以归因于该元数据条件，而非 LLM 分类波动。
- 范围：只测检索 Top20，不测最终 LLM 答案的文风或事实组织能力。

原始产物位于：

```text
tests/eval_rag/artifacts/metadata_eval/pilot-20260726-final-150508/
├── baseline_top20.jsonl
├── candidate_top20.jsonl
├── metrics.json
└── summary.md
```

## 逐类观察

### 单实体与别名题

神里绫华技能、狼的末路被动、迪卢克爆发，以及“绫华”“狼末”别名题在两种策略下都命中了对应 Gold Chunk，Hit@5、MRR@10、Recall@20 都为 1.0。

这符合预期：这些题已有唯一 `entity_id`，第一层“实体 + 类别 + 文档类型”就会命中；`element` 不应干扰这条精确路径。

### 元素集合题

| 问题类别 | Baseline 覆盖率@20 | Candidate 覆盖率@20 | Candidate Top5 错误块 |
| --- | ---: | ---: | ---: |
| 风系角色 | 17.65% | 100.00% | 0 / 5 |
| 冰系角色 | 27.78% | 100.00% | 0 / 5 |
| 火系角色 | 38.89% | 100.00% | 0 / 5 |

Baseline 没有元素约束，候选池会混入其他元素的角色资料；Candidate 在 `category=character` 和 `doc_type=character_profile` 基础上增加 `element`，所以 Top20 能覆盖当前 v7 语料中该元素的全部正式角色。

## 数据质量发现

首次运行发现少数历史导入的 MySQL Chunk 正文中文已经变为 `?`。这不是本次元数据过滤产生的错误：对应行的 `entity_id`、`doc_type` 和 `chunk_index` 仍正确，且 Candidate / Baseline 使用同一份已导入数据。

为了让评测不因正文乱码误判为“未命中”，本地评测端点额外返回了持久化的元数据；脚本按以下优先级恢复稳定 `logical_chunk_key`：

1. 正文 SHA-256 精确匹配源 Chunk；
2. 仅在唯一时，以 `entity_id + doc_type + chunk_index` 映射源 Chunk。

最终运行的未映射 Chunk 数为 0。乱码导入本身仍应另开修复任务：重建前需先定位旧导入批次，不能为了评测而直接覆盖生产数据。

## 局限与下一步

- 这是 10 题试运行，不足以形成简历中的大样本提升结论；扩展到 50–60 道人工复核题后，才适合稳定引用指标。
- 当前 Gold 对单实体题主要验证“至少有一个支撑块”，不衡量答案完整性；更严格的 nDCG、引用正确率和拒答准确率尚未建设。
- 领域外“银狼”仍是诊断题，当前项目没有完成可靠的领域外拒答机制，不能据此宣称已经解决幻觉问题。
- 本次报告只证明元数据分层检索的价值；尚未实现或验证 Contextual Retrieval，因此不能提前把它写入简历。

下一步按测试章程扩展测试集，并人工复核新旧结果发生差异的题目；随后再决定是否为错误召回率、集合覆盖率和延迟设置回归阈值。
