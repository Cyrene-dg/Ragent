# 原神知识库 v7：语义路由、结构化 Chunk 与元数据检索（最终成品复盘）

> 本文按**全部落实、完成验收后的成品**组织，用于面试复习与最终简历准备。所有 `X` 必须在真实评测完成后填写；它不是可以凭感觉补上的数字。

## 1. 今天为什么要动这个模块

最初的问题不是“向量模型不够强”，而是原神知识库的**目录、文档和检索范围没有真正连起来**：

1. 原意图树大量以角色名、版本名等命名；但同一知识库的叶子节点最后仍指向同一大集合。搜索“神里绫华”即使命中“神里绫华”节点，也没有把检索限定到她的 Chunk，树更像展示目录而不是有效路由。
2. 原神源 Markdown 基本是一篇文档对应一个 Chunk。角色档案等长文会把技能、命座、背景等混在同一大块里，召回命中后仍不够精确。
3. Chunk 没有 `entity_id`、`doc_type`、`section_path` 等可检索元数据。因此系统无法表达“优先在神里绫华的技能段中找；不足时再扩大到角色类资料”。
4. 现有 v4/v6 数据并存，且树的父节点关系曾只按 `parentCode` 拼接，跨知识库可能串树。直接原地删除、重建风险高。

这说明需要先修正知识组织方式，再讨论更复杂的 Agent、LLM 分块或 Contextual Retrieval。

## 2. 方案是怎样一步步定下来的

### 决策一：不删旧库，先平行构建 v7

- 保留 v4/v6 文档、索引和原 Markdown；
- 新建独立知识库 `genshin_kb_routing_v7` 和独立 Milvus collection；
- 先小样本验证，再全量导入；通过后才决定是否切默认检索路径。

理由：这个改造同时影响数据结构、向量索引和路由逻辑，不能拿线上旧数据做一次性实验。

### 决策二：树只表达“问什么”，不再把每个角色塞成意图叶子

v7 树是有限数量的**语义问题类型**，例如：

```text
原神知识库
├─ 角色资料
│  ├─ 角色基础资料
│  ├─ 技能与机制
│  ├─ 命之座
│  └─ 角色故事
├─ 武器资料
│  ├─ 属性与效果
│  └─ 武器故事
├─ 任务与章节
└─ 成就与收集
```

角色名、武器名等是另一张**实体目录（entity catalog）**，不是无限增长的树叶。这样：

- “神里绫华的元素战技是什么” → 语义意图是“角色 / 技能与机制”，实体是“神里绫华”；
- “雾切之回光的效果” → 语义意图是“武器 / 属性与效果”，实体是“雾切之回光”。

树负责选问题域，实体目录负责找具体对象；二者组合才能形成有意义的检索范围。

### 决策三：Chunk 必须带分层元数据，但不要把过滤写死

每个 v7 Chunk 会保存类似元数据：

```json
{
  "category": "character",
  "doc_type": "character_skill",
  "entity_type": "character",
  "entity_id": "avatar_10000002",
  "entity_name": "神里绫华",
  "section_path": ["角色技能", "元素战技"],
  "source_document": "avatars/avatar_10000002_神里绫华.md",
  "source_version": "v6"
}
```

不是所有 Chunk 都有实体：通用机制、章节、成就等可以没有 `entity_id`。同一角色的多个 Chunk 共享角色实体，但 `doc_type`、`section_path` 不同。

未来检索采用“实体强约束、意图软约束、结果不足再放宽”的策略：

```text
高置信实体 + 语义意图范围
→ 同实体所有段落
→ 同类资料
→ 全知识库兜底
```

这样既不会因为一条错误元数据把答案完全筛掉，也避免一开始就在全库盲搜。它不是“一个意图只对应一个叶子节点”的死规则。

### 决策四：只切过大的文档，优先按 Markdown 结构切

当前参数为：目标约 `760` 字符、最大 `1100` 字符、最小 `340` 字符、重叠 `80` 字符。

- 小而完整的成就、材料、短条目保持一块，避免过碎；
- 超长角色、武器、章节文档按标题层级切；
- 保留章节路径，不把“技能”“命座”“故事”混在一个 Chunk；
- 暂不使用 LLM 做全量切块：成本高、输出不稳定、难以复现。后续若发现复杂表格/无标题长文效果差，再把 LLM 作为少量兜底，而不是默认路径。

## 3. 最终成品实际落地了什么

### 数据层

- 从 `resources/genshin_seed_v6/docs` 读取 `6562` 篇 Markdown；
- 生成 v7 种子：`17` 个语义意图节点、实体目录、`7742` 个结构化 Chunk；
- 发现并结构化切分 `144` 篇超长文档，其中主要是角色、武器和任务资料；
- 本地校验：无空 Chunk、无超长 Chunk、无孤儿树节点、无旧“每角色一个意图节点”的泄漏。

生成脚本：`scripts/genshin/build_genshin_v7.py`；校验脚本：`scripts/genshin/validate_genshin_v7.py`。

### 存储与服务端

- `t_knowledge_chunk` 增加 `metadata_json`；
- Chunk 创建、更新、批量创建会持久化元数据；
- Milvus 向量记录保留 `kb_id/doc_id/chunk_index`，并合并 v7 元数据；
- 检索器支持把元数据筛选转换为 Milvus JSON filter；
- ES 同步沿用现有 Chunk 同步路径；
- 修复树构建按 `(kbId, intentCode)` 关联，避免跨知识库同名 `parentCode` 串树；
- 新增批量 Chunk 接口，允许导入器写入预生成的结构化 Chunk。

### 验证、导入与切换

1. Maven 编译通过；
2. MySQL 迁移已验证；
3. 新后端、Docker、Milvus、ES 均已启动；
4. 用 3 篇真实文档验证了 UTF-8 中文、数据库、Milvus 和 ES 写入链路；
5. 全量导入完成后，每篇文档都可由状态文件断点恢复；v7 数据、向量、关键词索引数量一致；
6. v7 通过离线评测和回归后设为默认路径，v4/v6 保留一段观察期作为回退。

过程中真实发现了两个 Windows PowerShell 导入问题：中文 JSON 默认编码不正确、单元素数组会被压成对象。两者都通过显式 UTF-8 字节和 `ConvertTo-Json -InputObject` 修复。这不是算法亮点，但面试中可以体现你做过端到端排障。

## 4. 成品必须具备的运行时闭环

最终不是“生成了一批带元数据的 Chunk”，而是下列闭环真正跑通：

1. 实体识别器把“神里绫华”等查询实体映射到 `entity_id`；
2. 语义意图 + 实体元数据过滤进入真实检索链路，并按结果数量、重排分数实现逐层放宽；
3. 用人工样本证明“分层范围检索优于直接全局检索”，并验证泛问法与错误实体不会被错误过滤；
4. v7 成为默认路径，v4/v6 在观察期内可一键回退；
5. 若后续需要进一步处理脱离标题仍不完整的 Chunk，再叠加 Contextual Retrieval，并以独立 A/B 实验判断是否启用。

前四项完成，才称得上“语义路由与元数据分层检索”成品；第五项是可选升级，不应和本模块混成一个已经完成的事实。

## 5. 怎么测试，指标先用 X 占位

至少准备三层测试集：

| 层级 | 样本例子 | 要验证什么 | 指标 |
| --- | --- | --- | --- |
| 路由 | “神里绫华元素战技是什么” | 是否识别角色/技能和实体 | Intent Accuracy、Entity Recall、全量回退率 |
| 检索 | “雾切之回光被动效果” | 正确段落是否在候选中 | Hit@5、MRR、过滤后候选量 |
| 回归 | 通用机制、模糊问法、跨类别问法 | 是否因过滤过窄漏答案 | Hit@5、无结果率、兜底触发率 |

简历里的数字在评测完成前统一写 `X`，例如：

> 在 `X` 条人工标注实体型问题上，Hit@5 从 `X` 提升至 `X`，全局候选量降低 `X%`，错误过滤后的兜底率为 `X%`。

这里的“人工标注”应是明确写出问题对应哪篇文档/哪一段的金标准；不能把现有弱标注集直接包装成人工金标。

## 6. 简历该怎么写

### 现有的第一条仍然适用吗？

**适用，且不要因为今天改 Chunk 就删掉。**

现有表述：

> 两阶段意图路由与歧义治理：规则/BM25/向量候选召回 → LLM 精判 → 低置信全量回退 → 同名意图澄清；在 1302 条弱标注样本中，Recall@80=100%，预过滤 P95=15ms，23/1302（1.77%）触发全量回退。

它描述的是原有系统的**意图候选预过滤和 LLM 精判机制**，指标也来自已有弱标注实验。今天的改造没有替代它。

### 差异是什么？

| 旧的“两阶段意图路由” | 今天的 v7 改造 |
| --- | --- |
| 解决“LLM 面对所有意图时 Prompt 过长、分类成本高” | 解决“选到意图后仍在大集合检索、长文语义混杂” |
| 规则/BM25/向量海选，再 LLM 精判 | 语义意图树 + 实体目录 + Chunk 元数据 + 逐层放宽 |
| 指标是候选覆盖率、P95、全量回退率 | 指标应是实体识别、Hit@5、MRR、候选量、错误过滤兜底率 |

二者在整条链路中是上下游关系：前者选“问什么”，后者把“到哪里找、如何不漏找”做实。

### 最终推荐升级第二条

不要额外堆成第六条；更适合升级“混合检索与重排”这一条：

> **语义路由与元数据分层检索**：针对实体型知识库中“命名实体意图树无法实际缩小检索范围”、长文单块混杂多个语义单元的问题，重构语义意图树与实体目录，按 Markdown 结构切分长文，并为 Chunk 写入类别、实体、文档类型和章节路径元数据；检索时采用实体优先、意图约束、全局兜底的分层召回，在 `X` 条人工标注问题上 Hit@5 从 `X` 提升至 `X`，候选规模降低 `X%`。

其中实体解析、分层放宽、评测数据和真实结果必须一并完成；否则简历暂时仍写原先的“混合检索、去重与 Rerank 后处理”，不把设计稿包装成成果。

## 7. 面试官会怎样问，以及如何不被问穿

### Q1：为什么不直接把“神里绫华”做成意图树叶子？

**回答骨架：** 角色名可以是实体，但不适合作为无限增长的语义意图树。旧树即使命中角色叶子，叶子下仍没有 Chunk 范围约束，不能真正减少候选；同时实体会持续增加、别名和版本会变化。v7 把“问技能还是故事”留给有限的语义树，把“是哪位角色”交给实体目录，再通过 Chunk 元数据组合过滤。

**追问陷阱：** 不要说“角色名的向量永远匹配不上叶子”。它可能匹配得上；真正的问题是匹配后没有形成对文档/Chunk 的可执行约束。

### Q2：每个 Chunk 都标元数据，会不会筛窄了漏召回？

**回答骨架：** 会，所以元数据不是绝对硬过滤。高置信实体先缩小范围；结果数量或重排分数不足时扩大到同类，再扩大到全库。通用知识没有实体字段，不会强行按实体过滤。评测必须包含错实体、别名、跨类别和泛问法，观察兜底率与漏召回。

### Q3：为什么最大 1100 字符、目标 760，而不是固定 token？

**回答骨架：** 这是一组当前可复现的起始工程参数，不宣称全局最优。目标是让一个技能/命座段尽量完整，同时避免角色长文整篇入库；短文不切，超长文按标题结构切，重叠只服务于跨段上下文。之后以 Hit@5、MRR、平均候选长度和延迟做参数 A/B，而不是靠直觉永久固定。

### Q4：为什么不用 LLM 直接给所有文档分块、打标签？

**回答骨架：** 全量 LLM 处理有成本、波动和难以复现的问题。源 Markdown 已有较稳定标题结构，第一阶段选择可复现的规则切分；实体 ID 来自已有结构化文件名/目录。只把 LLM 留给结构缺失文档或后续实验，不把它当作默认依赖。

### Q5：元数据放在哪里？Milvus 能过滤吗？

**回答骨架：** MySQL 的 `t_knowledge_chunk.metadata_json` 存事实数据与可追溯记录；写向量时把可用标量元数据合并进 Milvus 的 JSON metadata 字段，检索器把筛选条件转为 Milvus filter；关键词侧继续走现有 ES Chunk 同步。这样数据库是事实源，向量库和 ES 是检索索引，不把唯一事实只放在索引里。

### Q6：v4/v6 为什么不直接删掉重建？

**回答骨架：** 这不是单表迁移：MySQL、Milvus、ES、缓存和前端路径都有耦合。先建独立 v7，完成小样本、全量导入和查询对比后再灰度切换；旧库在验证期是回退保障。今天还修复了树按 `(kbId, intentCode)` 关联，避免跨知识库串树。

### Q7：这和原来的两阶段意图识别是什么关系？

**回答骨架：** 两阶段意图识别解决“从很多意图中快速选问题域”；v7 数据改造解决“选到问题域后怎样缩小到正确 Chunk，且不过度过滤”。前者是路由决策，后者是检索范围与知识组织；二者串联，不是重复功能。

## 8. 成品面试话术与事实边界

成品完成后可以这样概括：我发现旧树虽然能分类，却没有约束到具体 Chunk，且长角色文档一篇一块导致语义混杂；因此重构为“语义树选问题域、实体目录锁定对象、Chunk 元数据描述范围、低证据逐层放宽”的检索结构，并通过人工标注集验证检索质量和漏召回控制。

唯一不能模糊的是数字：`X%`、`X` 条样本、Hit@5、MRR、兜底率都必须能在评测脚本和样本文件里复跑。若 Contextual Retrieval 没有实际实施并评测，不能把它混进这条成品成果。
